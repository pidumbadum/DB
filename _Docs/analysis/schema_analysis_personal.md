# Анализ направления "Работа персонала"

## Основные таблицы

### personnel
Справочник действующих лиц системы (109 записей). Хранит не только реальных сотрудников, но и виртуальных акторов: кассовые узлы ("Касса 1"), службы ("Доставка"), системных пользователей ("Администратор Barnet").

Ключевые поля:
- **personid** — первичный ключ
- **firstname, lastname** — ФИО (у виртуальных акторов заполнены нестандартно)
- **securityaccess** — уровень доступа (9 = администратор, 3 = кассир, 1 = сотрудник)
- **flagpos, flagreports** — флаги прав (касса, отчеты)

### bm_BonusHistory
История бонусных операций. Связывает клиента (`ClientID`) и сотрудника (`PersonID`), проводившего операцию.

### bm_PersonnelSecurity, bm_SecurityObjects
Система разграничения прав. Для бизнес-анализа не критична.

## Проблема виртуальных акторов

Таблица `personnel` содержит три типа записей:
1. **Реальные сотрудники** — "Безик Татьяна Сергеевна"
2. **Кассовые узлы** — "Касса 1 Кафе 1" (продажи без авторизации кассира)
3. **Служебные акторы** — "Доставка Доставка" (агрегированные операции подсистем)

"Доставка Доставка" имеет 43 000 чеков на 42 млн — это не человек, а сумма всех заказов доставки. При анализе эффективности персонала такие записи нужно исключать.

**Критерии фильтрации:**
- Заполнены оба поля `firstname` и `lastname`
- `firstname` не содержит слов "Касса", "Доставка", "Администратор"

## Подтвержденные связи

Методом проверки данных (уникальные ID + висячие ссылки) подтверждены три связи:

1. **`journal.loginid` → `personnel.personid`**
   - 35 уникальных сотрудников, 0 висячих ссылок
   - Основная связь для анализа продаж (кто пробил чек)
   - `loginid` хранит `personid` в текстовом формате

2. **`bm_JournalBarnetDocs.PersonID` → `personnel.personid`**
   - 4 уникальных сотрудника, 0 висячих ссылок
   - Связь для анализа документов (кто оформил)
   - Малое число ID соответствует правам администраторов

3. **`bm_BonusHistory.PersonID` → `personnel.personid`**
   - Связь подтверждена
   - Позволяет анализировать бонусные операции по сотрудникам

## Связи между таблицами

```
personnel
    ├── journal (loginid) — кассовые операции
    ├── bm_JournalBarnetDocs (PersonID) — документы
    └── bm_BonusHistory (PersonID) — бонусы

bm_PersonnelSecurity
    ├── PersonID → personnel
    └── ObjectID → bm_SecurityObjects
```

## Примечания

- Для анализа продаж использовать `journal.loginid` с фильтрацией виртуальных акторов
- Для анализа ролей использовать `securityaccess` и флаги `flag*`
- Для анализа текучести кадров использовать `vw_PersonnelJobInfo` (поля `StartPeriod`, `StopPeriod`)
- Для отчетов удобно использовать `vw_Personnel` (готовые поля `fullname`, `SecurityName`)
- Таблицы `personnelmessages` и служебные таблицы безопасности для бизнес-анализа не нужны
