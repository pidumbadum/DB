# Анализ направления "Взаимоотношения с поставщиками"

## Основные таблицы

### vendors

Справочник контрагентов системы. Несмотря на название, таблица является универсальной и исторически хранит как поставщиков, так и клиентов. Содержит 63 записи. 

Ключевые поля для анализа:
- **id** — числовой первичный ключ таблицы. Именно это поле следует использовать для связывания с фактами операций.
- **firstname** — поле, в котором фактически хранится название контрагента (например, "ИП Габур", "5 Армия").
- **clientgroup** — ссылка на группу контрагента в таблице `vendorgroup`.
- **INN, KPP, OGRN** — реквизиты юридических лиц, позволяющие идентифицировать поставщиков для отчетности.

### vendorgroup

Справочник групп контрагентов. Классифицирует записи из таблицы `vendors`. Основная группа, представляющая интерес для данного направления — "Поставщики" (идентификатор 31).

### bm_StorageOperations

Единственный надежный источник фактических данных о взаимодействии с поставщиками в базе. Связь с таблицей `vendors` осуществляется через поле `VendorID`. Анализ показывает, что в базе активно используется 21 уникальный поставщик.

## Архитектурные особенности и качество данных

В ходе анализа направления была выявлена критическая особенность legacy-архитектуры системы, которую необходимо учитывать при построении аналитических запросов.

### Проблема "фантомных" связей
Колонка `vendorid` формально присутствует в нескольких ключевых таблицах базы данных: `product`, `pricelist`, `journal` и `bm_StorageOperations`. Однако проверка данных показала, что:
- В таблице `journal` колонка `vendorid` полностью пуста.
- В таблице `pricelist` колонка `vendorid` содержит только нулевые или пустые значения.
- В таблице `product` колонка `vendorid` заполнена лишь для единичных записей (фактически не используется).

Единственной таблицей, где связь с поставщиком работает корректно и заполнена реальными данными, является `bm_StorageOperations`. Следовательно, весь анализ поставщиков (обороты, ассортимент, динамика поставок) должен строиться исключительно на основе операций движения товаров.

### Несоответствие типов данных и именование ключей
В таблице `vendors` присутствуют два поля, которые могут быть восприняты как ключи: `id` (тип `bigint`) и `clientid` (тип `varchar`). 
- Поле `clientid` содержит строковые коды и не является надежным ключом для связывания. При попытке соединить числовые поля `VendorID` из таблиц операций с `clientid` возникает ошибка неявного преобразования типов данных.
- Поле `id` является корректным числовым первичным ключом. Все JOIN-операции с таблицей `vendors` должны выполняться исключительно по полю `id`.

## Связи между таблицами

```
bm_StorageOperations
    └── VendorID --> vendors.id (поставщик)
            └── clientgroup --> vendorgroup.vendorgroupid (группа контрагента)
```

## Примечания по использованию в аналитике

- Для расчета метрик по поставщикам (общая сумма закупок, количество поставленных позиций, периодичность поставок) необходимо фильтровать данные в `bm_StorageOperations` по условию `OperationID = 1` (Поступление).
- При анализе ассортимента конкретного поставщика следует использовать поле `ProductID` из таблицы `bm_StorageOperations` в связке с таблицей `product`, так как прямая связь `product.vendorid` не актуальна.
- Названия поставщиков для отчетов следует извлекать из поля `firstname` таблицы `vendors`, игнорируя поле `lastname`, которое в контексте поставщиков всегда пустое.
